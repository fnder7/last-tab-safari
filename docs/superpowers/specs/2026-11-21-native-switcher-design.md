# Last Tab: нативный переключатель вкладок — дизайн

Дата: 2026-11-21. Статус: черновик на согласование.

## Зачем

Сейчас у Last Tab две клавиши: ⌥E (меню с превью на сайтах, рисует content script) и ⇧⌘E
(команда Safari для быстрого возврата на Start Page). Одна клавиша делает одно, другая — другое,
и это неудобно. Нужно классное приложение: **одна клавиша и одна полоска с превью везде** —
на сайтах, на Start Page, на страницах самого Safari, в адресной строке.

Почему так нельзя в рамках web-расширения: на Start Page content script не запускается, а команда
Safari с сочетанием без ⌘ (⌥E) не срабатывает с клавиатуры (проверено: пункт меню с ⌥E есть, клик по
нему работает, нажатие — нет). Образец — TabBack: приложение в строке меню ловит клавишу глобально
(`RegisterEventHotKey` через библиотеку KeyboardShortcuts), до Safari.

## Цели

- Сочетание пользователя (у автора ⌥E; по умолчанию для новых установок остаётся ⌥Q, как сейчас
  в коде и README) открывает полоску вкладок текущего окна Safari в порядке MRU
  с превью, где бы ни был фокус в Safari.
- Поведение то же, что у нынешнего меню: держать ⌥ и нажимать E — вправо, ⇧ — влево, стрелки,
  отпустить ⌥ — переключиться, Esc — отмена, быстрый тап — сразу на предыдущую вкладку,
  несколько быстрых тапов подряд работают как сейчас.
- Работает в любой раскладке (клавиша по физическому коду).
- **Любое сочетание**, не только ⌥/⌃ + клавиша: любые модификаторы ⌘ ⌥ ⌃ ⇧ в любой комбинации
  плюс клавиша. Обязателен хотя бы один из ⌘ ⌥ ⌃ (иначе сочетание ломает набор текста, и нечего
  «отпускать» для переключения).
- **Два сочетания: «вперёд» и «назад».** «Назад» по умолчанию автоматически равно «вперёд» + ⇧
  и меняется вместе с ним. Его можно задать своё; тогда оно больше не следует за «вперёд»,
  а кнопка «Как вперёд + ⇧» возвращает автоматический режим. Если в «вперёд» уже есть ⇧,
  автоматическое «назад» невозможно, и пользователь задаёт его сам (до этого есть только
  «вперёд» и стрелки).
- **Настройка — в расширении, в кнопке на панели Safari** (попап, как сейчас; та же страница
  открывается из Settings → Extensions → Last Tab → Settings). Приложение берёт сочетания оттуда
  и сразу перерегистрирует клавиши.
- Полоска выглядит одинаково везде, это нативное окно поверх Safari (как Cmd-Tab).

## Не цели

- Chrome, Firefox, iOS.
- Переключение между окнами Safari или между приложениями.
- Поиск по вкладкам, закрытие вкладок из полоски.
- Несколько профилей Safari. У автора профилей нет. Данные в App Group всё равно хранятся
  с ключом профиля (`SFExtensionProfileKey`, appex его уже читает), чтобы поддержку можно было
  добавить позже; сейчас приложение берёт единственный профиль.
- Приватные окна. Как и сейчас, расширение в них не включено («Allow in Private Browsing» выключен),
  и полоска их не показывает. Если пользователь включит расширение для приватных окон, их вкладки
  в снимок не попадают (`tab.incognito`), чтобы ничего из приватных окон не писалось на диск.

## Анти-цели (провал, даже если «работает»)

- Нужны разрешения Accessibility или Screen Recording.
- Заметная задержка между нажатием и появлением полоски или переключением (ориентир — не хуже
  нынешнего меню на странице).
- ⌥E перехватывается в других приложениях: клавиша зарегистрирована только пока Safari активен.
- Снова две разные клавиши для одного и того же.
- Превью или список вкладок уходят куда-то с Mac.

## Ограничения

- macOS 26.5+, Safari 26+. Приложение и расширение в песочнице, подпись Personal Team (как сейчас).
- Расширение остаётся Safari web extension (MV3, непостоянный фоновый скрипт).
- Известная плата: пока Safari активен, ⌥E не вводит «´» (мёртвая клавиша) — ни в полях страниц,
  ни в адресной строке. Сейчас на страницах так уже и есть. У TabBack то же самое.

## Подходы

- **A. Нативная полоска везде (выбран).** Приложение в строке меню ловит клавишу, само рисует
  полоску, данные о вкладках и превью берёт у расширения, переключение просит у расширения.
  Одна клавиша, один вид, нет ограничений content script. Плата — много Swift и новая связь
  приложение ↔ расширение.
- **B. Гибрид.** На сайтах меню на странице, на Start Page — нативное окно; приложение пересылает
  нажатия в страницу. Два отрисовщика, которые будут расходиться, и лишняя задержка. Отклонён:
  та же несогласованность, только в другом месте.
- **C. Своя страница новой вкладки** (`chrome_url_overrides`). Без нативного кода, но пропадают
  Favorites и Privacy Report, а на страницах Safari и в адресной строке меню всё равно нет.
  Отклонён.

Выбран A: только он даёт одну клавишу и один вид везде.

## Как устроено

Три части: приложение Last Tab (в строке меню), нативный обработчик расширения (appex,
`SafariWebExtensionHandler`) и фоновый скрипт расширения.

```
 ⌥E ──► Приложение (строка меню)                      Safari
        • горячая клавиша, пока Safari активен
        • автомат состояний меню (порт menu-state)
        • нативная полоска ◄── читает ─── App Group ◄── appex ◄── sendNativeMessage ── фоновый скрипт
        • «переключи на вкладку N» ── dispatchMessage ──────────────────────────────► (порт connectNative)
                                                                                     tabs.update
```

### Фоновый скрипт (TypeScript, уже есть MRU и превью)

- Как сейчас ведёт MRU по окнам и снимает превью (`captureVisibleTab`, 400px JPEG).
- Следит за окном в фокусе (`windows.onFocusChanged`).
- При изменениях отправляет в appex снимок состояния через `browser.runtime.sendNativeMessage`:
  окно в фокусе; для него — вкладки в порядке MRU (id, заголовок, иконка, есть ли превью);
  новые превью отдельными сообщениями (id вкладки + JPEG). Отправки сглаживаются (debounce),
  чтобы не дёргать appex на каждое событие.
- Передаёт в appex сочетания «вперёд» и «назад» при запуске и при каждом изменении в
  `storage.local`.
- Держит порт `browser.runtime.connectNative` и принимает от приложения `activate {tabId}` →
  `tabs.update(tabId, {active: true})`.
- Нужно разрешение `nativeMessaging` в манифесте.

### Нативный обработчик (appex)

- Принимает сообщения фонового скрипта и пишет их в контейнер App Group: `state.json`
  (снимок) и `previews/<tabId>.jpg`. Удаляет превью закрытых вкладок.
- Сообщает приложению, что данные обновились (Darwin notification), чтобы оно могло держать
  их в памяти и не читать диск в момент нажатия.

### Приложение (Swift, AppKit)

- `LSUIElement`: без Dock, со значком в строке меню. Меню значка: текущие сочетания (только
  показ; меняются в расширении), «Запускать при входе» (`SMAppService.mainApp`), «Открыть
  настройки расширения» (как сейчас), выход.
- Горячие клавиши через Carbon `RegisterEventHotKey` (своя обёртка; KeyboardShortcuts не нужна,
  потому что запись сочетания — в расширении): «вперёд» и «назад» из App Group. Регистрируются,
  когда Safari становится активным (`NSWorkspace.didActivateApplicationNotification`), снимаются,
  когда нет. При изменении сочетаний — перерегистрация сразу.
- Отпускание: опросом `CGEventSource.flagsState(.combinedSessionState)` пока полоска открыта или
  идёт загрузка (без Accessibility). Переключение происходит, когда отпущен любой из модификаторов
  ⌘ ⌥ ⌃ сочетания, которым открыли полоску (как Cmd-Tab: отпустил ⌘ — переключился). ⇧ при этом
  не учитывается.
- Стрелки и Esc, пока полоска открыта: временные горячие клавиши, снимаются при закрытии.
- Автомат состояний — порт `src/content/menu-state.ts` на Swift один в один (с теми же тестами
  на Swift), чтобы быстрые тапы и прочие тонкости вели себя как сейчас.
- Полоска: неактивирующее `NSPanel` поверх всех окон, по центру экрана, на котором окно Safari
  в фокусе (рамка окна через `CGWindowListCopyWindowInfo`, без Screen Recording). Внешний вид
  повторяет нынешнее меню (`menu-view.ts`): карточки с превью, заголовком, иконкой, выделение.
- Переключение: `SFSafariApplication.dispatchMessage(withName:toExtensionWithIdentifier:userInfo:)`
  с `activate {tabId}`.

### Попап настроек (кнопка расширения на панели Safari)

Переделка нынешней страницы `options.html` (сейчас: выпадающий список модификатора + кнопка
записи клавиши). Две одинаковые строки записи, обе всегда видны: кликнул по строке и нажал
удобное сочетание. Выпадающий список модификатора уходит. Набросок:

```
 Last Tab
 Вперёд  ┌──────────────────────────┐
         │          ⌥ E             │   ← клик → «Нажмите сочетание…» → нажал → сохранено
         └──────────────────────────┘
 Назад   ┌──────────────────────────┐
         │        ⇧ ⌥ E             │   ← такая же строка; авто = вперёд + ⇧, клик — задать своё
         └──────────────────────────┘
           как вперёд + ⇧                 ← только когда «назад» задано вручную
 Держите модификаторы и жмите клавишу, отпустите — переключение. Esc — отмена.
 ⚠ Приложение Last Tab не запущено — Открыть     ← только если оно не отвечает
```

- Пока «назад» в авто-режиме, его строка показывает «вперёд + ⇧» и меняется вместе с «вперёд».
  После записи своего сочетания оно фиксируется; ссылка «как вперёд + ⇧» возвращает авто-режим.
- Запись: клик по строке, затем сочетание целиком (модификаторы + клавиша). Esc отменяет запись.
  Отклоняется: без ⌘/⌥/⌃; одинаковые «вперёд» и «назад».
- Сочетания, которые Safari забирает себе раньше страницы (например ⌘Q, ⌘W, ⌘T), записать
  не получится — попап их просто не увидит; это и хорошо, так как они всё равно конфликтуют.
  Для известных сочетаний Safari, которые попап увидит (⌘L, ⌘R и т. п.), показывается
  предупреждение «перекроет сочетание Safari», но сохранить можно.
- Формат в `storage.local`: `{ forward: {code, meta, alt, ctrl, shift}, reverse: <то же> | null }`,
  где `null` значит «авто: вперёд + ⇧». Старое значение `{modifier, code}` переводится в новый
  формат при чтении.
- Статус «приложение не запущено»: фоновый скрипт знает, отвечает ли приложение (оно
  подтверждает получение сочетаний через App Group). Как именно — на усмотрение исполнителя.

### Что уходит

- Content script, меню на странице (`src/content/`), команда `previous-tab` и ⇧⌘E. Логика
  `menu-state.ts` переезжает в приложение; файлы удаляются (остаются в истории git).
- `<all_urls>` в host_permissions остаётся: без него не работает `captureVisibleTab`.

## Риски и проверка первым делом

Перед основной работой — черновой прототип на выброс, чтобы проверить два непроверенных места:

1. **Будит ли `dispatchMessage` выгруженный фоновый скрипт** и с какой задержкой доходит
   `activate`. Запасной путь, если нет: AppleScript `set current tab of front window to tab N`
   (тогда в снимок добавляется индекс вкладки; появится запрос разрешения Automation — это
   допустимо, но хуже).
2. **Свежесть данных.** Успевает ли снимок в App Group обновиться к нажатию после переключения
   вкладки. Если нет — приложение при нажатии сначала показывает то, что есть, и обновляет
   полоску, когда придут свежие данные (как сейчас меню ждёт список).

## Решения, принятые без отдельного обсуждения (проверить при чтении)

- **Превью на диске.** Сейчас README обещает, что превью хранятся только в памяти. Теперь они
  лежат в контейнере App Group (`Library/Caches` группы), не покидают Mac, удаляются при закрытии
  вкладки и полностью — при каждом запуске приложения. Обещание в README меняется на «превью
  хранятся только на этом Mac, в кэше приложения, и стираются при закрытии вкладок».
- **Отправная точка.** Работа строится поверх текущего незакоммиченного состояния (1.1.0 со
  скриптами версий и CHANGELOG). Команда `previous-tab` и ⇧⌘E так и не выходили в релиз, поэтому
  их удаление — не изменение для пользователей. Новая версия — 2.0.0, запись в CHANGELOG.
- **Сочетание.** Сохранённое пользователем сочетание остаётся в `storage.local` и переводится в
  новый формат («назад» = авто). Кто не менял — остаётся на ⌥Q.
- **Отпускание при нескольких модификаторах.** Переключение по отпусканию любого из ⌘ ⌥ ⌃
  сочетания, ⇧ не считается.
- **Обязательный модификатор.** Без ⌘ ⌥ ⌃ сочетание не принимается (одиночные клавиши и
  ⇧ + клавиша ломают набор текста).

### Результаты прототипа (2026-11-22)

- `RegisterEventHotKey` в песочнице работает без Accessibility.
- Darwin-уведомление appex → приложение доходит сразу.
- `dispatchMessage` доходит до порта `connectNative` как `{name: "activate", userInfo: {tabId}}`,
  около 73 мс от нажатия до фонового скрипта.
- **Выгруженный непостоянный фоновый скрипт сообщение не будит** — оно теряется. Поэтому фоновый
  скрипт делается постоянным (`"persistent": true`; Safari на macOS это принимает).
- Один раз сообщение потерялось и при загруженном скрипте (первое нажатие после пересборки).
  Поэтому фоновый скрипт подтверждает `activate`, а приложение без подтверждения за 300 мс
  повторяет отправку один раз.
- Ответ appex на `port.postMessage` возвращается в тот же порт — фоновый скрипт в порт не пишет.
